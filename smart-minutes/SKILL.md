# Smart Minutes — 会议纪要 agent 落地方法论

## 它解决的痛点

**开完会不用回忆。录音落地成文字，要点自动提炼出来 —— 而且你随时知道它有多确定。**

三件事必须同时成立，缺一条这个产品就不成立：

| 部分 | 要求 | 做砸的后果 |
|---|---|---|
| **录得全** | 线下会走麦克风，线上会走系统声。两条路都得能录，且**不能丢音频** | 录了三小时的会少了十分钟，而你不知道 |
| **存得住** | 音频、逐字稿、要点**都留在本机**。这是产品承诺，不是可选项 | 一次泄露就毁掉整个产品的信任基础 |
| **提炼准且自知** | 出要点的同时给**置信度和依据**；判错了看得见、一键能改 | 结论无法质疑，用户要么盲信要么弃用 |

**第三条是这类产品最容易做砸的地方，也是本 skill 的重点。**
大多数同类产品只给结论 —— 那等于把"机器判断"包装成了"事实"。

---

## When to invoke this skill

用户要做一个**录音 → 本地存储 → 自动出会议要点**的 agent，或已经在做但卡在下面任一处：

- 线上会议的**系统声**录不下来
- 长录音**一次塞不进模型**，或塞进去质量崩了
- 转写模型**不给时间戳**，要点里没法标"约第几分钟"
- 有"**数据不出本机**"的硬约束，不知道怎么设计数据流向
- 模型判错了用户不知道 —— 需要一个**纠错通道**

**不要**用于：一次性把录音转成文字（不需要 agent）、实时字幕、
说话人分离的算法本身（那是另一个问题）。

## 一、先定输入形态，再选技术栈

**输入形态决定架构。** 先回答这三个问题，答案会砍掉一半的技术选型：

| 问题 | 影响 |
|---|---|
| **线下还是线上？** | 线下 = 麦克风；线上 = 系统声（WASAPI loopback / 虚拟声卡）。**两者都要支持** |
| **一次多长？** | 决定了必须分块，以及必须能断点续跑 |
| **有没有 GPU？** | 没有 GPU 就必须纯 CPU 推理，速度是整个产品的可行性上限 |

### 先量后选：不写 bench 就开始写代码，是最贵的错误

老硬件上的性能不是"快一点慢一点"，是**能不能用**。

bench 的设计要求：

| 要求 | 为什么 |
|---|---|
| **用真实素材**，不用公开测试集 | 决定准确率的是你的**领域词**，不是通用词频 |
| **测端到端时间**，不只测模型加载 | 用户感知的是总时长 |
| **相同配置连跑 3 次** | 确认是**确定性**的。否则后面的对比全部无效 |
| **候选 ≤3 个** | 超过 3 个，你会开始按偏好选 |

> 参照量级：在一台**无可用 GPU 的老笔记本**上，纯 CPU 转写 181 秒中文会议音频 ≈ 17 秒
> （RTF≈0.095）。换算下来**3 小时会议 ≈ 17 分钟**。
> 这个数决定了产品可行性，而它只能量出来，猜不出来。

## 二、录音层

### 两种音源，一个混合器

```
麦克风线程 ─┐
            ├─→ 以最长的轨为基准，短的补零 → 混合 → 落盘
系统声线程 ─┘
```

**关键设计（每一条都是踩过的）**：

| 设计 | 理由 |
|---|---|
| 每路音源**一个独立线程** | 互不阻塞。一路卡住不影响另一路 |
| 停止时以**最长的一路**为基准 | 短的补零而不是截断到最短 —— **绝不丢尾部** |
| 实时电平暴露给 UI | **录音最怕的是静默失败**，必须有可见反馈 |
| 多轨混合时先除轨数 | 防止叠加削波 |

### 音频掉块：光加优先级不够，必须对账

录音线程被饿死（典型场景：后台正在跑转写，CPU 全占满）时，
音频缓冲溢出，掉的是**永久丢失的音频**。

**对账公式：**

```python
captured_ratio = 实际采到的样本数 / (墙钟时长 × 采样率)
```

`ratio < 0.99` 就告警，并且要说清**后果**：

> ⚠ 录音中间掉了约 N 秒（采到 97%）。**时间是错的**，别按逐字稿的时间去对原始录像。

**「时间戳会前移」这句必须提。** 掉块之后所有后续时间点都会偏移；
用户不知道的话，会拿逐字稿的时间去对视频，得出"这工具不准"的结论 —— 而真因是音频丢了。

### 关窗必须接管

**默认的关窗行为会静默丢掉一切。** 桌面 GUI 的 `mainloop` 直接退出、进程结束，
录音线程是 daemon 跟着一起死 —— `stop()` 和 `save()` 根本不会执行。

```
录了三小时的会，手滑点个 X 就全没了，且没有任何症状。
```

处理四件事：**弹确认框说清后果 → 同步停止并保存 → 流水线在后台跑完 → 窗口销毁后改走控制台输出**。

## 三、转写层：模型不给时间戳，就自己造

### 取舍：准的模型常常没有时间戳

非自回归模型（如 SenseVoice 一类）**整段进整段出** —— 快、准、多语种，
但**不输出任何时间信息**。而下游全都需要：逐字稿要标分钟数、要点要能定位、
说话人分离要按时间轴对齐。

### 解法：用 VAD 的语音段边界当时间戳

```
音频 → VAD 找语音段 → 在静音边界合并成固定长度的窗口 → 每个窗口单独送 ASR
```

**块的边界就是时间戳。** 在静音处切断，天然不会切碎句子。

顺带白拿三个好处：

| 好处 | 说明 |
|---|---|
| 省时间 | 静音不送进模型。真实会议远没有测试样本那么密 |
| 天然的进度单位 | 每块跑完存一次盘 —— **长录音崩了不用从头来** |
| 内存可控 | 3 小时音频不会一次性进内存 |

### 窗口大小必须量出来，不能凭感觉

**准确率不是随窗口单调上升的** —— 实测中出现过"窗口翻倍反而丢词"的情况。
所以这个参数只能扫出来：

```python
WINDOW_SEC = <扫出来的值>   # 依据见下方实测表，别凭感觉改
```

把那张实测表**连同"别凭感觉改"一起写进文件头**。参数一旦量出来，
它就不再是代码，是结论。

### 两个必踩的实现坑

| 坑 | 现象 | 修法 |
|---|---|---|
| **音频不能整段灌进 VAD** | 缓冲区是环形的，灌满就溢出。实测整段灌入 → **只切出 1 个 0 长度的空段** | 小块喂，**边喂边取** |
| **样本必须在 `pop()` 之前读走** | pop 后底层缓冲被回收。实测：**段数对、时长全是 0.00s** | 先 `.copy()` 再 `pop()` |

> 第二条特别隐蔽 —— 段数是对的，只有时长不对。**"检查每段时长 > 0"这一行如果不写，
> 这个 bug 会一路带到生产**，表现为所有时间戳都是 00:00。

## 四、本地存储：这是产品承诺，不是可选项

### 架构约束：全系统只有一个网络出口

把**所有**外发调用收进一个模块，其他地方一律不许直接发请求。

**价值：「数据有没有出本机」变成可审计的问题** —— 查一个文件就能回答，
而不是 grep 整个代码库。

### 最小必要集

不要问"要不要上云"，要问**"出本机的最小必要集是什么"**。

典型答案：**音频、录音、说话人特征永不出本机；只有转写后的文字可以出。**

这个拆解把"要么全本地、要么全上云"的二选一，变成了**三档可控**：

| 档位 | 行为 | 适用 |
|---|---|---|
| **提炼关闭** | 只出本地逐字稿，**一个字都不出本机** | 敏感会议 |
| **提炼开启** | 仅转写文本出本机 | 日常 |
| **一键清空** | 音频、逐字稿、要点、索引**同删** | 事后反悔 |

### 粒度决定一切

**开关粒度必须到「每一次会话」，不是全局设置。**

全局开关是个一次性决定 —— 用户要么全开、要么全关，遇到敏感的那一场只能不用这个工具。
每会话开关让他**今天开、明天关**，工具才真的会被持续使用。

### 验证方式（能证伪的那种）

> 关掉开关跑一次 → **断言网络无任何外发请求**，只有本地产出。

"检查是否保护了隐私"不能失败，等于没写。"断言无外发请求"能失败，写它。

### 删除必须一次清干净几处

典型是**四处**：音频、逐字稿、要点、检索索引。
**少清一处就是留尾巴** —— 用户以为删了，其实还能搜出来。

## 五、置信度：本 skill 的核心

### 要设计掉的失败模式

用户最不能接受的情况不是"它做错了"，而是"**它做错了，而我不知道**"。

一个只输出结论的模型，把一个概率判断包装成了事实。
用户只有两个选择：盲信，或者全部人工核对（那还不如自己做）。

**置信度 + 依据 + 一键纠正，把这个失败模式设计掉。**

### 三个必须同时给出的东西

```json
{"verdict": "...", "confidence": 0.92, "reason": "..."}
```

| 字段 | 作用 | 只有结论会怎样 |
|---|---|---|
| `verdict` | 结论 | — |
| `confidence` | **分流量级**。高了直接看，低了重点核对 | 用户无法分配注意力 |
| `reason` | **可质疑的依据** | 结论不可质疑 = 不可信 |

**三个一起给，用户才有得判断。** 给结论不给依据，等于要求盲信。

### 呈现规则

| 规则 | 理由 |
|---|---|
| 置信度**显示在结论旁边**，不折叠、不藏在设置里 | 它是结论的一部分，不是元数据 |
| 低于阈值时**显式提示"不太确定，建议核对"** | 把用户的注意力引到最该看的地方 |
| 依据**必须显示**，允许截断但不允许隐藏 | 用户靠它判断该不该信 |
| **永远给一个纠正按钮** | 见下 |

### 一键纠正的工程要求：纠正只能重跑提炼

**这是整个设计能不能成立的关键。**

| 步骤 | 耗时量级 | 纠正时 |
|---|---|---|
| 转写 | 分钟级（3 小时录音 ≈ 十几分钟） | **绝不重跑** |
| 提炼 | 秒级 | 只重跑这一步 |

如果纠正要重跑转写，"判错了也不要紧"就变成了空话 —— 用户会为了省时间而忍受错误结论。

**实现方式**：把流水线的中间状态持久化（checkpoint），
纠正时**从被纠正的那个节点重新开始**，不碰前面的节点。

> 参照：完整流水线 27 秒的输入，只重跑提炼约 5 秒。

### 置信度的诚实边界（必须告诉用户）

**模型自报的置信度不是校准过的概率。**

它的价值在于**排序**（哪个更可疑），不在于绝对值。
所以产品里不要写"95% 准确率"这种话，要把它用做**分流**：

```
高置信 → 直接看要点
低置信 → 重点核对，或直接点纠正
```

把它如实定位成一个**注意力分配工具**，而不是一个准确率承诺。

## 六、长录音：两级提炼

长录音转出来的逐字稿**一次塞不进模型**。

```
逐字稿 ≤ N 字 ─→ 一次调用直接产出
逐字稿 > N 字 ─→ MAP（分段提事实）→ MERGE（合并成要点）
```

`N` 取决于模型上下文，典型取值在 1–3 万字之间（约 1 小时左右的对话）。

| 要求 | 理由 |
|---|---|
| **在段边界切**，不按字数硬切 | 硬切会把句子劈成两半，模型读到半句会**脑补后半句**，脑补内容混进结果 |
| 每组带上**自己的起止时间** | MAP 提示词里的"约第 N 分钟"来自这里 |
| MAP 的 system prompt 写明"**你只看到一个片段**" | 不写，模型会在片段里找"整场主题" —— 它看不到，于是编一个 |

## 七、绝不静默

贯穿全系统的原则：**任何一步失败都记进 `errors` 并标 `partial`，如实说。**

### 最危险的不是崩溃，是"悄悄给出错误结果"

| 失败模式 | 危险度 | 处理 |
|---|---|---|
| 崩溃 | 低（会被发现） | 记 `errors` |
| 明确报错 | 低 | 记 `errors` |
| **判断失败后硬套一个模板** | **高** | **不许**。跳过提炼，只交逐字稿，标 `partial` |
| **模型脑补未出现的内容** | **高** | 提示词里写死"原文没有的不编，标未提及" |

### 提示词里的"不编"要写成可执行规则

不要写"不要编造"，要写**具体判断规则** + **找不到时的输出**：

> - 只写逐字稿里真实出现过的内容。没说的不补、不推测、不美化。
> - 待办事项：事项 + 责任人 + 时间点（**原文没有的就不编，标"未提及"**）
> - 没有就写「无」。

**「没有就写无」这一句是必须的。** 不写的话，模型面对空集默认会编一个像样的。

### 用户身份决定输出内容，不只是措辞

同一个录音，不同的使用者要的东西完全不同：

| 使用者 | 要什么 |
|---|---|
| 参会者 | 决议、待办、谁负责 |
| 汇报者 | 自己讲了什么、哪里没讲清楚 |
| 被评估方 | 自己哪几句答短了、哪几处被追问（**只要事实，不要评价**） |

**先确定使用者是谁，再写模板。** 同样的转写文字，给错人就是废纸。

## 八、环境踩坑：通用排查顺序

### 原生扩展一加载就段错误

在没有独显的老机器上，**新版原生推理扩展经常一加载就崩**。
症状看起来像硬件坏了或驱动问题，实际是**新编译的二进制用了这颗 CPU 不支持的指令**。

```
1. 降版本  ← 绝大多数问题在这一步解决
2. 查 setuptools（老版本可能还要 pkg_resources，81+ 已删除该模块）
3. 最后才查 DLL / 驱动 / VC++ 运行库
```

**不要一开始就去翻 DLL、查 CPU 厂商。** 那是最后一步，也是最浪费时间的一步。

**记账纪律**：把根因写进 `requirements.txt` 注释，**并且写行动指令**：

```
# >>> 换机器若报段错误，先怀疑这几条版本，不要先去查 CPU 厂商。<<<
```

写"为什么钉这个版本"不够 —— 要写到让下一个人知道**下次遇到同样症状先做什么**。

> **归因纪律**：诊断时**一次只改一个变量**。
> 同时改两处，你得到的是"现在能跑了"，而不是"因为什么能跑"。

### 触发条件依赖数据规模的分支，要专门造样本测

短路径天天跑、天天绿，长路径只在真实长会议时才走到。
**只要一条分支的触发条件依赖输入规模，就必须专门造一个够大的样本来测它。**

## 九、交付层（面向非技术用户时）

| 坑 | 现象 | 修法 |
|---|---|---|
| **批处理文件存了 UTF-8** | Windows 的 cmd 按 GBK 逐字节解析，中文的**字节碎片会被当命令执行**。文件头的 `chcp 65001` **救不了** —— 解析早就跑偏了 | 批处理一律存 **GBK** |
| **脚本建的快捷方式不刷新** | 用脚本创建的 `.lnk`，桌面**不会自动出现** | 建完通知 shell 刷新 |
| **桌面是唯一入口太脆** | 被窗口盖住 / 拖走 / 多显示器跑丢 | **开始菜单也放一份**，搜索能搜到 |
| **图标渲染成纯白** | 颜色按 0–255 存、alpha 按 0–1 存，末尾又统一乘 255 | **统一量纲**：要么全 0–1，要么全 0–255 |

> 最后一条的规律：图像管线里混用量纲，错误会以"看起来完全无关"的方式表现出来
> （形状对、颜色全错）。要么全 0–1，要么全 0–255，**别混**。

## 落地顺序（照这个顺序做）

```
1. 量硬件：跑 bench，确定最慢的环节和真实耗时        ← 决定产品可不可行
2. 定数据流向：画出唯一外发通道 + 最小必要集 + 开关粒度
3. 打通录音：两种音源 + 混音 + 电平反馈 + 掉块对账
4. 打通转写：VAD 合成时间戳 + 实测窗口大小 + 断点续跑
5. 接提炼：单块直路 → 多块 MAP/MERGE
6. 加置信度：三字段输出 + 呈现规则 + 一键纠正（只重跑提炼）
7. 本地检索：中文分词器选型 + 删除要清干净几处
8. 交付层：启动入口 + 失败时能看懂的错误提示
```

**第 1、2 步不能跳过，也不能后置。** 它们决定的是"要不要做"和"能不能做"，
而不是"怎么做"。

---

## 已知局限（说清楚，不装作没事）

- **纯 CPU 转写速度是这类产品的根本瓶颈。** RTF≈0.1 意味着 3 小时音频要等十几分钟。
  如果使用场景是"开完会立刻要纪要"，这个延迟就不可接受 —— 那就该去谈云 ASR，
  而不是继续优化本地推理。**在选型阶段就把这个问题摆给用户。**
- **本方法论来自单条产品线的落地经验**，不是跨场景的统计结论。
  硬件相关的具体版本号**只对同类环境有效**，但**排查顺序**（先降版本、
  再查 setuptools、最后查 DLL）适用范围更广。
- **模型自报的置信度未经校准验证。** 本 skill 把它定位为注意力分配工具，
  没有声称它能当概率用。如果你的场景需要真实概率，得自己做校准集。
- **说话人分离不在本 skill 范围内。** 两人音色相近时会串，
  这是独立的技术问题，不要和上面这些混在一起解决。
- **长录音的断点续跑是设计而非保证。** checkpoint 机制能不能真的扛住强杀，
  必须在真实的长时间录音上验证过才能说"支持"。
- **面向第三方分发时还有一整套问题未覆盖**：安装包、模型分发、首次运行下载、
  多用户隔离。本 skill 假设**开发者就是使用者**。
