# build-the-agent-you-want-most

> 把一句模糊的「我想要一个能…的 agent」锻造成**能跑起来的东西** ——
> 苏格拉底式追问 → 张小龙式反驳 → agent solution → 落地 → 思维链留痕 → 反思。

## 它解决什么问题

你有一个 agent 想法。它现在长这样：

```
我想要一个能自动整理会议纪要的 agent。
```

这句话里缺的东西，比它说出来的多得多。而**你不会在开始做之前发现它们** ——
你会做到一半才发现"录音到底存哪"、"模型判错了怎么办"、"这东西真的有触发场景吗"。

这个 skill 把那句模糊的话，逼成一份**用户签字确认过的方案**，再做出来。
七个阶段，顺序不能换：

```
0 找出不可变核心原则 → 1 苏格拉底式追问 → 2 张小龙式反驳（三轮）
   → 3 得出 agent solution → 4 确认后才动手 → 5 落地执行 → 6 反思总结
```

前四个阶段是**把想法逼清楚**，后三个阶段是**把它做出来并留下为什么**。
两边缺一半，这个 skill 就退化成"陪聊"或者"写代码"。

| 阶段 | 产出 | 材料 |
|---|---|---|
| 0 找核心原则 | 一句**逐字引用**的话 | `SKILL.md` |
| 1 苏格拉底追问 | 矛盾清单 | [`QUESTION-BANK.md`](QUESTION-BANK.md) |
| 2 张小龙式反驳 | 三轮 + 诚实记账表 | [`STEELMAN.md`](STEELMAN.md) |
| 3 得出 solution | 七节落地方案 | [`PLAN-TEMPLATE.md`](PLAN-TEMPLATE.md) |
| 4 确认后才动手 | 用户明确点头 | `SKILL.md` |
| 5 落地执行 | 能跑的东西 + **思维链留痕** | [`LANDING.md`](LANDING.md) |
| 6 反思总结 | 三问复盘 | [`LANDING.md`](LANDING.md) |

## 三个不可越过的闸门

这三条是整个流程的价值所在。**违反任何一条，它就退化成"陪聊 + 写代码"。**

| 闸门 | 规则 | 违反的后果 |
|---|---|---|
| **不动手闸门** | 阶段 0–3 全程**不装依赖、不写实现代码、不部署**。用户明确点头，才进阶段 4 | 用户还没想清楚你就开始写，写出来的东西大概率全废；而且他失去了"改主意"的机会 |
| **原话闸门** | 核心原则必须**逐字引用**用户原话，写进方案的显眼位置，并标注"不可变" | 你转述一遍就丢失了精度。后面所有推导都建立在这句话上，转述等于在沙子上盖楼 |
| **记账闸门** | 每一条被你收回的反对意见，都要**公开列表说明为什么收回** | 用户看到你会认输，才会相信你没认输的那些是真问题 |

> **为什么"不动手"要单独设一个闸门。**
> 因为对一个 agent 来说，"给方案"和"开始做"之间的诱惑太大了 ——
> 顺手写个原型看起来是帮忙，实际上是把用户的思考过程短路掉了。
> 用户点头之前，一个字都不写。

## 里面的几个关键动作

### 核心原则必须是**原话**，不是你的转述

用户最初说的往往是**手段**（"我想用 LangGraph 做"、"我想本地跑"），不是**目的**。
反复问"为什么"，直到他给出的那句话，**他自己会承认不容让步**。

> **实战样本**（一个「录音 → 本地存储 → 提炼要点」的产品）：
> 用户原始需求是"做个会议记录工具"。追问多轮后，他给出的是：
>
> > "LLM 基于转成文字后的会议内容，推理判断是会议还是面试，再进行会议要点／面试要点的提炼，
> > **而不是通过两个版本迭代的方式进行实现**。"
>
> 注意这句话里有**两件事**：一个功能要求，和一个**否定**。
> 那个"而不是"往往比正面的要求更关键 —— 它排除了你最容易走的那条路。

### 反驳是 steelman，不是唱反调

**构造你的反对意见最强的版本，然后看它站不站得住。**
反过来做（先立个稻草人再打）毫无价值，用户会立刻发现你在走过场。

检验方法：把你的反驳说给用户听之前，先问自己
"**如果我是他，我会觉得这条被驳倒了吗？**"

三轮的分工：

| 轮次 | 攻击什么 | 必须用的语言 |
|---|---|---|
| 第一轮 | **可行性** —— "你这台机器上做不出来" | 数字，不是形容词 |
| 第二轮 | **必要性** —— "做出来了你真的会用吗" | 他自己的场景，不是泛泛之谈 |
| 第三轮 | **后果** —— "它做对了，副作用你受得了吗" | 具体机制，不是担心 |

### 落地阶段的思维链留痕

**前四个阶段逼出来的判断，如果不写进代码和文档，它们只存在于聊天记录里。**

三类必须留，按价值排序：

| 类型 | 例子 |
|---|---|
| **根因 + 行动指令** | 不是"段错误"，是"新二进制用了这颗 CPU 不支持的指令 —— 换机器若报同样症状，先怀疑版本，不要先去查 CPU 厂商" |
| **量出来的参数** | 任何"扫出来的"数，连同那张实测表一起写进文件头，标注**别凭感觉改** |
| **被推翻的假设** | 完整的推翻路径：我曾断言 X → 实测发现 Y → 排除法 + 剂量-反应 → 修正为 Z |

> **第三类最值钱，因为它校准的是你的判断力本身。**
> 断言错了不可怕，可怕的是用一个新断言去覆盖旧断言。

### 选型表里不写框架名

方案里有一张**按「需求」组织、不按「产品」组织**的选型表：

| 需求 | 候选机制 | 选它的前提 | 代价 |
|---|---|---|---|
| **可续跑** | ① 框架自带 checkpointer ② 自己维护「已完成单元」清单 ③ 分段产出直接落盘 | ①的前提是跑得动那个依赖 | ① 引入依赖；②③ 要自己写恢复逻辑，但零依赖 |

**硬规则：每一行必须挂在一条核心原则，或 M1 量出来的一个数上。**
两个都挂不上的，标注「这是偏好，可改」。

> 为什么不写死框架：**阶段 0 的全部工作就是不许把手段当目的。**
> 样本确实用了图框架，但那是被硬件数字定出来的结果，不是模板给的答案。
>
> 而且框架不替你做纪律 —— 样本用了带 checkpointer 的框架，
> 交付时仍然只能写「断点续跑是**设计而非保证**」。

## 已知局限（说清楚，不装作没事）

- **本方法来自单一产品线的落地经验**，不是统计结论。苏格拉底式追问在
  **愿意被追问**的用户身上效果最好；面对"你别问了照做就行"的情况，应直接跳到阶段 3，
  但要**明确告知跳过了什么**。
- **阶段 0 有失败模式：用户给不出"不可变"的那一句话。** 那通常意味着他自己还没想清楚，
  此时正确动作是**继续问或建议先别做**，而不是替他编一条然后当成他的原则往下推。
- **阶段 2 的"三轮"是上限不是配额。** 第一轮就被驳倒三条时，继续硬凑三轮会显得在找茬。
- **诚实记账需要你顶住自我辩护的本能。** "你说得对，我错了"后面不接**具体的失效机制**，
  等于没认。
- **本 skill 不覆盖"想法本身是坏的"这种情况。** 如果三轮下来核心原则站不住，
  正确输出是告诉他别做，而不是产出方案。
- **阶段 5 的思维链留痕是有成本的。** 记太细会拖慢落地，记太粗等于没记。
  [`LANDING.md`](LANDING.md) 给的是取舍标准，不是"什么都记"。
- **落地步骤是通用的八步，不是万能的。** 它的价值在**顺序原则**（先做最不确定的那件事、
  不可再生数据先落盘），具体到一个领域仍要重排。
