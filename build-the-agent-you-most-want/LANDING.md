# 落地：步骤 · 思维链 · 反思

阶段 5 和阶段 6 的全部内容。**用户点头之后看这里。**

分三部分：

| 部分 | 回答的问题 |
|---|---|
| **一、落地步骤** | 按什么顺序做 |
| **二、思维链留痕** | 边做边记什么、怎么记 |
| **三、反思总结** | 跑完之后怎么复盘 |

三部分是一件事的三个面：**步骤是"做什么"，思维链是"为什么这么做"，反思是"当初该不该这么做"。**
少了第二部分，前四轮逼出来的那些判断会在落地过程中悄悄流失；
少了第三部分，你会重复犯同一个错，而且每次都以为是新问题。

# 一、落地步骤

## 总原则：先做实验，不做地基

**M1 必须是"最不确定的那件事"，不是"最容易的那件事"。**

先搭目录、先配环境、先做最容易的模块 —— 这是最常见的排期错误。
它让前三天过得很舒服，然后把"这事到底做不做得成"这个问题推到第五天才回答。
如果答案是不能，前三天全废。

> 样本里 M1 是"跑 bench 量出转写速度"。因为这个数决定**产品可不可行**，
> 不是一个可以留到后面优化的参数。

**判据**：M1 结束之后，你应该能回答"这事能不能做成"。
如果你只得到了"环境配好了"，M1 排错了。

## 八个步骤

顺序不能换。第 1、2 步**不能跳过也不能后置** —— 它们决定的是"要不要做"和"能不能做"，
而不是"怎么做"。

```
1. 量最不确定的那件事        ← 决定可行性。做不出数就不往下走
2. 定数据流向               ← 唯一外发通道 + 最小必要集 + 开关粒度
3. 打通输入层               ← 先把"能拿到数据"跑通，处理逻辑留空壳
4. 打通核心处理             ← 最重的那个环节，断点续跑
5. 接上模型 / 提炼          ← 概率环节，和确定性环节分开
6. 加质量层                 ← 置信度、降级、纠错
7. 存储与检索               ← 可追溯、可删除
8. 交付层                   ← 启动入口 + 失败时能看懂的错误
```

### 每一步的判据

| 步 | 做完的标志 | 没做完硬往下做的后果 |
|---|---|---|
| 1 量数据 | 有一张**实测表**，不是估算 | 后面的所有排期都是猜的 |
| 2 定流向 | 能回答"数据出不出本机、出哪些" | 隐私约束会推翻已经写好的架构 |
| 3 输入层 | 真实素材能进来，落盘了 | 拿假数据调出来的参数全是错的 |
| 4 核心处理 | 中途强杀能续跑 | 长输入一跑就崩，且要从头再来 |
| 5 接模型 | 失败时**不丢上游产出** | 模型一挂，前面的活白干 |
| 6 质量层 | 判错了用户看得见、能改 | 用户要么盲信要么弃用 |
| 7 存储检索 | 删除一次清干净全部副本 | 用户以为删了，其实还搜得到 |
| 8 交付 | 双击能起，报错能看懂 | 只有你能用 |

### 三条贯穿全程的纪律

**1. 一次只改一个变量。**

同时改两处，你得到的是"现在能跑了"，不是"因为什么能跑"。
后者才是能复用的知识，前者只是个巧合。

> 诊断时尤其如此。症状消失不等于你找到了原因 —— 也可能只是被另一个改动掩盖了。

**2. 触发条件依赖输入规模的分支，要专门造样本测。**

短路径天天跑、天天绿；长路径只在真实长输入时才走到。
**只要一条分支的触发条件依赖输入规模，就必须专门造一个够大的样本来测它。**

> 样本里的教训：分段处理的路径只有超长输入才会触发，平时永远测不到，
> 结果第一次真的走到就崩了 —— 而且崩在一个只有那一行才有的拼写错误上。

**3. 不可再生的数据在第一步就落盘。**

音频、原始素材、用户手写的草稿 —— 这类东西丢一次就永远没了。
**它们必须早于任何可能失败的步骤写进硬盘。**

> 样本里逐字稿在转写节点就写盘，**早于所有模型调用**。
> 后面模型无论怎么失败，那份文字都已经在硬盘上了。

### 绝不静默

贯穿全系统：**任何一步失败都记进错误列表并标记为"部分完成"，如实告诉用户。**

最危险的不是崩溃，是**悄悄给出错误结果**：

| 失败模式 | 危险度 | 处理 |
|---|---|---|
| 崩溃 | 低（会被发现） | 记进错误列表 |
| 明确报错 | 低 | 记进错误列表 |
| **判断失败后硬套一个模板** | **高** | **不许**。跳过这一步，交出已有的部分，标记为"部分完成" |
| **模型编出输入里没有的内容** | **高** | 提示词里写死"原文没有的不编，标未提及" |

**"没有就写无"这一句必须写进提示词。** 不写的话，模型面对空集默认会编一个像样的。

# 二、思维链留痕

## 为什么必须留

前四个阶段逼出来的判断 —— 核心原则、收回的反对、量出来的数字 ——
**如果不写进代码和文档，它们只存在于聊天记录里，而聊天记录会丢。**

三个月后你回来看这段代码，看到的是一堆"为什么这么写"。
留痕的作用是：**让未来的你（或别人）能重建你当时的推理，而不是只能选择相信或推翻。**

**留进代码，不是留进对话。** 这是唯一的区别。

## 什么时候必须留

三类，按价值排序：

### 第 1 类：根因 + 行动指令（最值钱）

**"段错误"不是根因，"新二进制用了这颗 CPU 不支持的指令"才是** ——
区别在于前者无法据此做任何决定。

而且**要写到让下一个人知道下次遇到同样症状先做什么**：

```
# <依赖名>==<版本>
#     <更高版本> 一加载就崩（access violation），新版二进制在这颗 CPU 上跑不动。
#     <中间版本> 是另一个毛病：打包 bug，启动时去找一个不存在的目录。
#     <当前版本> 实测能正常加载。
#
# >>> 换机器若报同样症状，先怀疑这三条版本，不要先去查 CPU 厂商。<<<
```

最后那句是**行动指令**，不是解释。写"为什么钉这个版本"不够 ——
要写到下一个人能据此**做决定**。

> 排查顺序同样值得写死：先降版本 → 再查打包/构建工具 → **最后才查驱动和运行库**。
> 反过来查，会浪费大量时间在一个从一开始就不相关的地方。

### 第 2 类：量出来的参数

**任何"扫出来的"参数，都要把那张实测表连同"别凭感觉改"一起写进文件头。**

```python
WINDOW_SEC = <扫出来的值>   # 依据见下方实测表，别凭感觉改
```

参数一旦量出来，**它就不再是代码，是结论**。写成裸数字，下一个人会当成随手填的默认值改掉。

> 样本里的实测表还有一个反直觉的结论：**准确率不是随窗口单调上升的** ——
> 出现过"窗口翻倍反而丢词"。这类发现不写下来，一定会有人再踩一次。

### 第 3 类：被推翻的假设

**这一类最值钱，因为它校准的是你的判断力本身。**

记法不是"我错了"，是**完整的推翻路径**：

> 我曾断言"分块能提升准确率"。实测发现**第一版分块结果比整段还差**。
> 于是做排除实验：
>
> 1. 先排除上下文假设 —— 窗口合并后结果仍然一致
> 2. 再排除随机性 —— 连跑三次，结果相同
> 3. 最后做**剂量-反应测试** —— 逐步加大窗口，证明准确率**随窗口单调上升**
>
> 结论修正为"分块确实有代价，只是被窗口大小掩盖了"，并把那张表写进了代码。

**注意这个过程：断言错了不可怕，可怕的是用一个新断言去覆盖旧断言。**
排除法 + 剂量-反应，才是把"我觉得"变成"我量过"的路径。

## 什么时候不用留

记太细会拖慢落地，记太粗等于没记。**取舍标准：**

| 该记 | 不该记 |
|---|---|
| 不可逆的决定，以及为什么选它 | 显然的写法、语言常识 |
| 量出来的数字，和量它的方法 | "这里改了 XX 让它能跑"（没说为什么） |
| 踩过的坑：症状 → 真因 → 下次先做什么 | 一次性的环境抖动 |
| 与直觉相反的发现 | 与直觉一致的发现 |
| **没有**采纳的方案，以及否掉它的理由 | 采纳了的方案的功能描述（代码本身就是） |

最后一条常被忽略：**否掉的方案比采纳的更值得记。** 代码里看不到"为什么不是另一种写法"，
下一次你会把同样的弯路再走一遍。

## 交付时的进度留痕

长流程一定要有**可打断、可解释**的进度。

用户等 20 分钟时，要能看到"正在做第 3/7 段（约 40–60 分钟）"，
而不是一个转圈的图标。

**要解释，不要只报数** —— "3/7" 不如 "正在转写第 3 段，这一段约 8 分钟"。
前者用户不知道还剩多久，后者他知道。

# 三、反思总结

跑完必须产出。**不是走流程，是三个必须回答的问题。**

| 问 | 要写什么 | 为什么 |
|---|---|---|
| **哪些反对意见我收回了？** | 复盘诚实记账：收回对了吗？有没有当时该坚持却让步的？ | 收回是你的判断，判断需要被检验 |
| **哪些判断被实测推翻了？** | 我给过、后来被数据打脸的结论 | **最值钱的一类**。它校准的是判断力本身，不是这个项目 |
| **还有什么是未知的？** | 不能装的"已知局限" | 把"我以为我知道"变成"我知道我不知道" |

## 怎么写才不是走过场

**第一问的判据**：能不能说出**当时那条反对意见的具体前提是什么**。
说不出，说明你只是记了个"我认输过"，没有复盘价值。

**第二问的判据**：有没有**具体的数字或实验**。写"我低估了性能问题"是废话；
写"我估 30 分钟，实测 90 分钟，差在 X"才是复盘。

**第三问的判据**：这些局限**会不会影响用户的决策**。
"可能有兼容性问题"是废话；"没在真实长输入上强杀验证过，所以不能说支持断点续跑"才是。

## 反思的产物往哪放

| 产物 | 去处 |
|---|---|
| 根因、实测表、被推翻的假设 | 进代码注释 / 文件头 / 项目 README |
| 已知局限 | 进交付文档，**明写出来**，不藏在心里 |
| 方法本身的教训 | 进你自己的流程（下次这类项目的步骤该怎么改） |

**第三条最容易漏。** 一个项目跑完，你学到的不该只是"这个项目怎么做"，
还有"这类项目下次该怎么排、哪个环节最容易估错"。

> 样本里最值钱的一条自省不是技术结论，是**方法论**：
> 断言错了不可怕，可怕的是用一个新断言去覆盖旧断言。
> 这条留在方法里，比留在代码里有用得多。

## 最后：诚实

反思里最没用的三种写法：

| 写法 | 为什么没用 |
|---|---|
| "整体顺利，达到预期" | 没有信息量，等于没写 |
| "主要问题是时间不够" | 把原因推给外部，下次还会不够 |
| "以后要注意 XX" | 没有可执行动作，等于没写 |

**合格的反思读起来是难受的** —— 因为它记录的是你判断失误的地方。
如果复盘读完觉得很舒服，你多半只是在总结成绩。
