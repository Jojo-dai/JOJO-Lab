# 张小龙式反驳：三轮协议

阶段 2 的全部打法。

## 这个手法的内核

张小龙做产品时的标志性动作，不是"提出好想法"，是**对每一个功能反复问"为什么需要它"**，
问到提出者自己都答不上来为止。它有效的机制是：

> **把一个功能的举证责任，从"反对者需要证明它有害"翻转为"支持者需要证明它必要"。**

默认状态是"不做"。想做？给理由。

所以这里的"反驳"不是唱反调 —— 是**替用户把他自己没做的功课做掉**。
真正好的反驳，用户看完会说"对，这个我确实没想"，
而不是"你懂什么"。

### steelman 与稻草人的区别

| | 稻草人（无效） | steelman（本协议要求） |
|---|---|---|
| 攻击的是 | 你没说过的、容易打的版本 | 你说过的最强的版本 |
| 用户的反应 | "我没这么说" | "对，我确实是这么想的" |
| 用了 | 形容词（"这可能不稳定"） | 具体机制 + 数字 |
| 结果 | 消耗信任 | 建立信任 |

**检验方法**：把你的反驳说给用户听之前，先问自己"**如果我是他，我会觉得这条被驳倒了吗？**"
如果你自己都觉得是抬杠，删掉重写。

## 第一轮：攻可行性

**"这东西在你这台机器 / 你的时间预算上做不出来。"**

这一轮必须**全部用数字**，不用形容词。"性能可能不够"是废话，
"3 小时音频跑 90 分钟，你开会 3 小时要等 1.5 小时"是反驳。

### 怎么构造

1. 找出**最慢 / 最重 / 最不确定**的那个环节
2. 用用户给出的硬件和时间预算，**算一遍**
3. 如果算不出来，**那就是第一个要做的实验** —— 把它写进方案的第一步

### 话术模板

```
这条路上最慢的是 {X}。按你给的 {硬件/预算} 估，
{输入规模} 要跑 {时间}。你的场景是 {真实频率}，
意味着 {具体的难受之处}。

退路有三条，各有代价：
- {退路 A}：代价是 {Y}
- {退路 B}：代价是 {Z}
- {退路 C}：与你的核心原则冲突，需要你拍板
```

> **样本**：3 小时会议音频在无 GPU 的老笔记本上可能跑 45–90 分钟。
> 这条直接被写成了方案的第一条风险，并推出了"M1 第一件事就是量出这个数"。

**关键**：可行性反驳**不要给结论，给退路**。用户比你清楚他能忍受到什么程度。

## 第二轮：攻必要性

**"就算做出来了，你真的会用吗？"**

这一轮最难，因为它攻击的不是技术，是用户自己。要用**他自己的场景**去攻，
不能用"一般人不这么用"这种泛泛之谈。

### 四个经典的"做了但没用"路径

| 路径 | 症状 | 攻法 |
|---|---|---|
| **录入成本 > 收益** | 用之前要准备 10 分钟，省下的只有 5 分钟 | "你每周用几次？准备一次要多久？" |
| **信任不足** | 输出要人工全量核对，那还不如自己做 | "它给你的东西，你敢直接拿去用吗？不敢的话你会核对多少？" |
| **触发点缺失** | 功能很好，但没人记得去用它 | "你在什么时刻会想起来打开它？" |
| **改进无感** | 用了和没用差别不大 | "上一次遇到这个问题时，你实际怎么解决的？" |

> **样本**：用户是面试里的**候选人**，不是面试官。这个身份差异决定了
> "面试要点"该输出什么 —— 他不需要"候选人评估"，他需要
> "我哪几句答短了、哪几处被追问了"。如果做成通用面试记录工具，
> 输出会是给面试官看的评估报告 —— 功能对了，人不对。

### 话术模板

```
我不确定你会在什么时候打开它。
具体说：{场景} 的时候，你手上已经有 {现有替代品}，
而它 {比现有方案强在哪} —— 但代价是 {多出来的步骤}。

你上次遇到 {场景} 是怎么处理的？
```

## 第三轮：攻后果

**"它做对了，但副作用你受得了吗？"**

这一轮专攻**成功后的问题**。三轮里它最容易被跳过，却最常变成上线后的真问题。

### 三个必查的副作用维度

| 维度 | 问什么 | 典型后果 |
|---|---|---|
| **数据流向** | 做对这件事，需要把什么送出本机？ | 与"本地/私有"的核心原则冲突 |
| **维护成本** | 三个月后它还跑得动吗？依赖会烂吗？ | 模型接口变了、版本升级炸了、磁盘满了 |
| **信任稀释** | 它开始判错了，你会怎么反应？ | 把关键判断交给概率模型，久了会不再信任它的任何输出 |

> **样本里的第三条**最终成了方案里"保留的分歧"：
>
> > 把产品最重要的判断交给概率模型，长期看会稀释你对它输出的信任。
> > 缓解手段已内建（置信度 + 一键纠正 + 保留原始逐字稿）。
>
> 注意措辞：**"缓解手段已内建"** 而不是 "所以不用担心"。
> 分歧保留了，用户知道这件事存在，选择权在他。

## 诚实记账：怎么写才不像敷衍

每轮结束后的固定动作。**这是整个方法可信度的来源** ——
用户看到你会认输，才会相信你没认输的那些是真问题。

### 格式

```markdown
| 我之前砍的 | 收回理由 |
|---|---|
| {你的反对意见原文} | {推翻它的**具体机制**} |
```

### 判据：收回理由里必须有一个可检验的机制

| 敷衍（无效） | 合格 |
|---|---|
| "你说得对，我错了" | "我的反对理由是 X，但 X 的前提是 Y；Y 不成立，因为 Z" |
| "考虑到你的需求，我调整一下" | "**该失败模式可被设计掉**：{具体怎么设计}" |
| "这样也行吧" | "双模板是 `structure` 节点内的分支，**不是两个产品**" |

**规律**：收回理由里要能看到**你原来那条反对意见的确切前提被打破**。
用户能分辨"你真的被说服了"和"你懒得争了"。

### 收回之后必须做的事

1. **把收回的条目放进方案开头**，不藏进附录。
   放在前面才会被读到；藏进附录，等于假装没说过。
2. **检查有没有"被收回但没被解决的"** —— 有些反对意见，
   用户的回应只是"我知道，但先不管"。那不算收回，那是**已知风险**，
   要原样写进方案的「诚实风险」一节。
3. **保留没被说服的部分。** 三轮下来一定还有你不同意的地方。
   写出来，标明"不在方案里争论，但你应知道"。

## 什么样的反驳是无效的

按出现频率排序：

| 无效反驳 | 为什么无效 | 改成 |
|---|---|---|
| "这样可能有问题" | 没有具体失效路径，用户无法据此决策 | "当 X 发生时，会导致 Y，代价是 Z" |
| "业界一般不那么做" | 诉诸惯例，用户可以直接不听 | 给出**具体的环境约束**（"2GB 显存跑不动"） |
| 一口气列 20 条 | 稀释了真问题，用户只会挑软柿子捏 | 每轮 2–3 条，**最硬的排第一** |
| 反对完不给替代 | 等于只说"不行"，把难题丢回去 | 每条反对**必须**配"但可以这样绕过" |
| 攻击用户的动机 | "你其实不需要这个" | 攻击**机制**："这个机制在 X 条件下会失效" |
| 提了反对又自己圆回来 | "不过当然啦你决定" —— 等于没提 | 提了就让它站着，让用户处理 |

## 三轮之后

| 情况 | 动作 |
|---|---|
| 大部分反对被驳倒 | 用户的方案站得住 → 进阶段 3 出方案。**诚恳说明你被打服了** |
| 大部分反对站住了 | 方案有硬伤 → **不要出方案**。把问题摊开，建议改方向或先做实验 |
| 一半一半 | 走实验路线：把站住的那些反对，**变成方案的第一个里程碑**，先量再定 |

> 第三种情况最常见，也最有价值 —— 它把"我们谁也说服不了谁"变成了
> "两天的实验就能定"。**把争论转成实验，是这个过程最该产出的东西。**
>
> 这条实验路线怎么落成 M1、怎么在落地时执行，见 [`LANDING.md`](LANDING.md) 的第一部分。

### 与阶段 6 的呼应

三轮里"站住了但你没能当场解决"的反对意见，**不会消失**。
它们要么变成方案里的「诚实风险」，要么变成落地后的「已知局限」。

阶段 6 的第一个问题 —— **"哪些反对意见我收回了？收回对了吗？"** ——
就是回头检查这一节。**收回是你的判断，判断需要被检验。**
