# 落地方案模板

阶段 3 的骨架。**七节，缺一不可，顺序不要换。**

顺序本身就是设计：先钉住原则（1），再公开你认过的输（2），
然后展示只有你能给出的那部分推理（3），最后才是工程细节（4–7）。
反过来写就成了普通的技术方案 —— 那种文档用户看完不会纠正你，
因为他看不出哪里可以纠正。

---

## 0. 头部

```markdown
# {产品名} — {一句话定位} · 落地方案 v{n}

> 代号 `{codename}`，目录 `{path}`。名字可改。
> **硬性 deadline：{日期}。**        ← 有就写，没有就删掉这行
```

**"名字可改"这类话要写。** 它告诉用户：小决定不必现在纠结，先看大结构。

---

## 1. 用户不可变的核心原则（原话，不得删改）

```markdown
> **"{逐字引用的用户原话}"**

拆成三条硬约束：

1. {约束一} —— {它是从原话的哪个词推出来的}
2. ...
```

**三条纪律**：

- 标注"原话，不得删改"，并且**真的不要改**（包括错别字和口语）
- 每条约束后面写出**它对应原话的哪个部分** —— 让用户能检查你的拆解有没有过度解读
- 这一段要放在**最前面**。它不是背景介绍，它是后面所有内容的依据

---

## 2. 我收回的反对意见（诚实记账）

```markdown
## 我收回的两刀（诚实记账）

| 我之前砍的 | 收回理由 |
|---|---|
| "{反对意见原文}" | {推翻它的具体机制} |

**保留的分歧（不在方案里争论，但你应知道）**：{你依然不同意的地方}
```

标题带**数量**（"两刀"）比"我的反思"这种模糊标题好 —— 它暗示你数过，是真的在记账。

放在第 2 节而不是附录，是刻意的：**它决定了用户后面会不会认真读你的推理。**
一个肯在开头认输的人，后面提的风险才有人信。

写法细节见 [`STEELMAN.md`](STEELMAN.md) 的「诚实记账」一节。

---

## 3. 由你的原则推出的新后果（必须在方案里正面处理）

```markdown
> **{一句话说明张力}**

{张力是怎么从核心原则里推出来的}

因此方案把它做成**三档可控**，由你决定：

| 档位 | 行为 | 适用 |
|---|---|---|
| ... | ... | ... |

**粒度到"{单位}"，不是全局。** {为什么粒度很重要}
```

**这一节是整个方案里最能体现你价值的地方。** 第 1、2 节是转述和认输，
第 4–7 节是工程常识 —— 只有这一节是用户自己想不到的。

写不出来怎么办？回到阶段 0 重读核心原则，问自己：
**"这条原则如果严格贯彻，会推翻用户已经默认的哪个选择？"**

> 判据：如果用户看完只说"对对对"，你多半只是复述了他已知的东西。
> 如果他说"这我没想到，那确实得处理一下"，才做对了。

## 4. 架构

```markdown
```
┌────────┐   ┌──────────────────────┐   ┌────────┐
│ {组件} │──▶│ {流水线/模块序列}     │──▶│ {存储} │
└────────┘   └──────────────────────┘   └────────┘
                              │
                      ┌───────┴────────┐
                      │ {外发点，如果有} │  {它发什么、不发什么}
                      └────────────────┘
```

**一键 = {用户的操作从几步变成几步}。**
```

然后每个模块一张表，**必须包含"失败姿态"列**：

| 节点 | 职责 | 断点 | 失败姿态 |
|---|---|---|---|
| `{name}` | | ✅ / — | {失败时怎么办，绝不能写"报错"} |

**"失败姿态"这一列是这个模板里最容易被写空的。** 合格的写法长这样：

- 单块失败 → 重试 3 次 → 跳过并记入 `errors`，**绝不静默**，最终交付"已完成 / 被卡住"清单
- LLM 调用失败 → **绝不丢弃逐字稿** —— 先保底，再提炼
- 判断失败 → **不猜、不硬套模板**，状态标 partial，如实说

> 为什么"报错"不合格：它没有说清失败之后**剩下什么**。
> 用户要知道的是"我还能拿到多少"，不是"它出错了"。

---

## 5. 里程碑

```markdown
| 阶段 | 内容 | 天 |
|---|---|---|
| **M1** | {最不确定的那件事的实验} | n |
| **M2** | {核心原则落地} | n |
| **M3** | {质量升级} | n |
```

**排序依据不是技术依赖，是"用户最在意的东西什么时候能用上"。** 并且要**写出你的依据**：

> 样本原句：
> "**M2 结束，你的核心原则就已全部落地** —— LLM 判类型 + 双模板提炼都在。
> M3 的分人是质量升级，不是功能前置。
> （这也是我原本坚持"M2 就可用"的同一个判断，只是把 LLM 段从 M3 提前到了 M2 ——
> 因为它是你的核心原则。）"

写出依据，用户才能在你排错时纠正你。不写依据，他只能接受或推翻整张表。

**M1 必须是"最不确定的那件事"**，不是"最容易的那件事"。
先做地基、把风险留到最后，是最常见的排期错误。展开见 [`LANDING.md`](LANDING.md)。

---

## 6. 验证方式

每条断言配一个**可执行、能证伪**的检查：

```markdown
1. **{选型}对比（M1）**：{同样的输入}，跑两个方案，记录 {指标}。**用数据选型。**
2. **端到端**：{具体操作} → 断言 {文件} 和 {文件} 都存在，{数据库} 有索引。
3. **{关键承诺}**：关掉 {开关} 跑一次 → 断言**网络无任何外发请求**，只有本地产出。
4. **删除**：删一次会话，断言 {N} 处**同时**清干净。
```

**判据：这条验证能不能失败？** "检查输出质量是否良好"不能失败，等于没写。
"断言网络无任何外发请求"能失败，写它。

**不能证伪的验证项等于没写** —— 它只会给用户一种"验过了"的错觉。

---

## 7. 诚实风险

```markdown
1. **{最大的不确定性}。** {具体数值/条件}。{退路，以及退路的代价}。
2. ...
```

**三条纪律**：

- **第一条必须是能用数字描述的。** "可能有性能问题"是废话，"3 小时音频跑 45–90 分钟"才是风险
- **每条都要给退路，并写出退路的代价。** 只说"有风险"是把焦虑转嫁给用户
- **如果退路与核心原则冲突，明说需要拍板。** "换云 ASR（但与'本地'冲突，需你拍板）" ——
  这个括号是整段里最重要的部分

## 交付前自检

- [ ] 核心原则是**逐字引用**，带引号，没被我"整理"过
- [ ] 收回的反对意见在**第 2 节**，不在附录
- [ ] 第 3 节里有一条是**用户没说过的**
- [ ] 每个模块都有**失败姿态**，且没有一条是"报错"
- [ ] 里程碑**写明了排序依据**，且 M1 是最不确定的那件事
- [ ] 验证方式**每条都能失败**
- [ ] 第一条风险**有数字**
- [ ] 明确写了"**你点头我才动手**"

**最后一条不能省。** 方案给完就停在那里等确认 ——
见 [`SKILL.md`](SKILL.md) 的阶段 4。
